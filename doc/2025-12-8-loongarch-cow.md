# RISC-V 到龙芯架构的COW机制移植说明
## 项目概述
本README记录了在将写时复制（Copy-on-Write, COW）机制从RISC-V架构移植到龙芯架构过程中遇到的关键问题及其解决方案。研究发现两种架构在页表权限位的行为上存在显著差异，需要通过不同的硬件位来实现COW机制。

## 问题描述
RISC-V中的标准实现
在RISC-V架构中，COW机制通常使用页表项（Page Table Entry）中的PTE_W位（写权限位）来触发写入例外：

初始设置：共享页面的PTE_W位被清除（设为0）

写入触发：进程尝试写入时，由于PTE_W=0，触发Store/AMO Page Fault

内核处理：陷入usertrap，执行COW复制流程

权限恢复：为新页面设置PTE_W=1

龙芯架构中的问题
将相同的实现移植到龙芯架构时，发现以下问题：

COW机制失效：写入共享页面时未触发例外

程序崩溃：多个进程直接修改同一物理页面，破坏数据一致性

硬件行为差异：虽然龙芯页表项中也有类似PTE_W的位，但其行为与RISC-V不同

## 硬件位功能对比
架构	写入控制位	功能描述
RISC-V	PTE_W	控制页面是否可写入，PTE_W=0时写入触发例外
龙芯	PTE_D (脏位)	控制页面是否可写入，PTE_D=0时写入触发例外
龙芯	PTE_W	功能未明确描述写入触发，实际测试不触发例外
## 文件修改清单
需要修改的核心文件
text
kernel/vm.c
    - uvmcopy()            # 进程复制时的页面映射
    - copyout()            # 内核到用户的复制
    
kernel/trap.c
    - usertrap()           # 用户例外处理
    - cow_handler()        # COW专用处理函数
架构相关定义

## 已知问题与限制
性能影响：龙芯架构中通过PTE_D位实现COW可能需要额外的TLB刷新

兼容性：此实现针对qemu龙芯架构版本，不同型号可能需要调整

并发处理：在多核环境下的COW竞争条件需要仔细处理
